## 3. UDP 缺口与后续要求

固定内核[规则匹配源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.33/tunnel/tunnel.go#L684)
在 UDP 命中不支持 UDP 的出口时会继续匹配后续规则。本次来源末尾为 MATCH,DIRECT，
因此单成员落地组能约束 TCP，却不能单独保证该场景的 UDP 不绕出。

已实测的对照规则：

```yaml
- AND,((NETWORK,UDP),(DOMAIN,claude.p0.invalid)),REJECT
```

这里的失败针对未加拦截规则的现有编译输出，不表示已经加载严格 UDP 拒绝规则仍然绕出。
产品策略现已明确：严格模式显式拒绝命中受保护服务规则的应用 UDP，不以 ISP 支持 UDP
为放行理由，不默认阻断整机 UDP。前置底层传输与应用 UDP 分别处理。

以上对照仍仅覆盖合成域名。新增服务策略生成时，生成对应的 UDP 拒绝规则，并验证
域名排除、无关服务 UDP 及原规则保持；普通模式的 UDP 转发能力另行验证。
不能一概声称 udp 字段或 disable-udp 已解决，也不能把本次对照误记为产品修复。
当前 README 的固定落地表述已补充这一适用范围。
ChatGPT/Codex 的具体严格约定及该组对照范围见 [F010](F010-GPT严格模式.md)。

  保留最新元数据并更新下载信息，当前订阅随后重新应用；已有脚本持久性值得验证，不能只靠改原 YAML。
- [配置生成](https://github.com/chen08209/FlClash/blob/7fd417fb9a9a277c6a9339a8ac87f907df7c25f7/lib/providers/actions/setup.dart#L494)

尚未证明：外部工具怎样可靠安装/刷新脚本及让运行中的客户端识别；已有标准扩展或脚本
怎样共存；切到未接管或新订阅前是否有持续覆盖的挂载点；恢复时怎样保留后续用户修改。
不采用切换后再补写来冒充全程持续约束，也不未经核验就改正在运行的数据库。

## 5. 下一步及进入 P1 的条件

1. 准备不会访问日常客户端数据、不会影响本机 TUN/系统代理的桌面验证环境。
   当前仅具备独立内核环境，尚未配置上述 GUI 隔离环境。
2. 针对两款固定发布版本，确认可逆安装位置、更新触发机制和用户扩展共存方案，再做真实
   更新/切换/重启/后台停止/恢复场景。FlClash 的逐订阅挂载与新订阅窗口是重点。
3. 补自动前置故障切换；将严格服务 UDP 拒绝及无关 UDP 保持纳入正式回归。
   支持 UDP 的代理转发属于普通模式的独立验证，不作为严格模式的放行目标。
4. DNS 解析器实测需自有或获准使用的权威域名观测/回查服务，当前未选定依赖。
   本地浏览器 STUN 检测仍不能单独证明特定服务的路径；未部署外部探测服务。

持久覆盖、用户扩展共存和独立恢复仍是 P0 未完成条件，不能把本轮局部验证记作 P0 全通过。
复现入口、组件职责和预期非零退出见 [P0 运行说明](../tests/p0/README.md)。
