## 2. 四层怎样对应这个项目

采用依赖方向 L3 -> L2 -> L1 -> L0。目录仍按业务和 Python 约定命名，不强制创建四层空目录。

| 层 | 本项目责任 | 边界 |
| --- | --- | --- |
| L0 公理 | 稳定 ID、出口种类、配置/测量结果契约等最小事实 | 按所属模块保存，不放网络、磁盘、HTTP 状态或可变全局状态 |
| L1 积木 | 域名/代理解析、Mihomo 校验和拓扑、原子存储、单个网络能力 | 有清晰输入输出，隐藏实现，不编排多模块业务 |
| L2 流程 | 模块内的配置准备、资源变更、客户端应用/恢复、检测流程 | 拥有模块内部事务和状态变化，不操作其他模块私有状态 |
| L3 外交 | 协调服务配置、客户端应用、恢复记录及检测的跨模块动作 | 只使用公开流程和必要契约，不解析代理地址、不拼 DNS/控制器协议 |

HTTP 在最外层不自动等于 L3。server.py 目前主要是传输适配，继续保持薄入口；
真正的 L3 是业务模块间的应用/恢复协调，当前 GatewayService 包含其中一部分。
GatewayService 还混有 L1/L2，不能直接给整个文件贴上 L3 标签就视为完成分层。

现有纯编译 API 可继续作为明确公开的 L1 深积木复用，无需为它创建无意义的 L2 转发函数。
这是有意保留的公开积木例外。除这类明确公开面外，跨模块协调默认经过 L2，
同层内部协作限于同一业务模块。确有共享能力时先声明归属和公开契约，不引入循环。

## 3. 最小拆分顺序

### 先整理阅读入口，不增加运行组件

使用[功能索引](索引.md)和[当前页](../任务进展/当前.md)定位任务。

对应文档。索引只保存摘要与链接，当前页只记录正在做、下一步和验证信息。
长文按相关章节阅读；在出现独立主题或重复维护问题时再分页，不按固定行号切开。

### P1：把独立计算移出大流程

- 代理地址解析有约 117 行独立逻辑，批量导入前优先提为落地域的能力，供单条和多条复用。
  它当前抛 GatewayError，提取时不能反向导入 gateway；解析错误归本模块，流程层负责转换。
- 新服务策略放在有明确归属的模块，复用编译积木；不要继续增加 GatewayService 私有方法。
- 编译器按 YAML/引用校验、拓扑构造、编译入口评估拆分。保持现有公开调用与脱敏语义；
  必须提取契约时仅提本模块必要类型，不创建全局 types/constants 杂物库。

### P2：按完整所有权分离状态与流程

- 状态和生成版本的读写、迁移、原子提交归同一存储能力，保留一致的提交边界。
- 资源变更与跨模块应用流程分开。L3 使用公开计划/提交/恢复结果，不能直接操作 _state。
- 不把 GatewayService 拆成一组共享 self._state 的 mixin，也不为每类资源建立近似的仓储类。
- 订阅快照管理将退出主流程，过渡期维护兼容；不提前为这部分建设完整新框架。

### P3：随实际页面拆前端

- 先分离页面结构、样式和脚本；实际增加服务/ISP/设置视图时，再按视图及 API/状态拆分。
- 公共弹窗、错误和请求行为只保留一份；保留现有滚动和焦点修复。
- 不机械复制后端 L0-L3 目录，不为单个按钮创建组件文件，不为拆文件强制换框架。
- 静态资源拆开时同步实现服务端明确的资源映射并测试，避免只有 / 能访问而新脚本 404。
