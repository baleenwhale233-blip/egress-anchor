| 场景 | 结果 | 证据与边界 |
| --- | --- | --- |

## 3. FlClash 结果

| 场景 | 结果 | 证据与边界 |
| --- | --- | --- |
| 标准追加规则基线 | 通过 | 合成用户规则实际进入运行内核 |
| 直接从 standard 改成 script | **未通过共存要求** | 原规则还在数据库，但不再进入运行规则；固定落地本身可用 |
| 显式组合已知测试追加规则 | 通过局部对照 | 原规则与落地同时生效；原型只支持这一条合成 DOMAIN 规则，非通用迁移器 |
| 原生更新 A v2 → v3 | 通过 | 脚本关联保留，新节点进入前置，用户规则及落地路径保持 |
| 切到全新 B | **未通过持续约束** | B 是 standard、无脚本关联；实际走回机场 OriginalAI，没有经过指定落地 |
| 切回 A、客户端重启 | 通过局部对照 | A v3 关联和落地保留；重启后在原生界面启动代理才进行流量验证 |
| 选择性恢复并保留更新 | 通过原型对照 | 只恢复 A 的 extend_type/script_id 并移除自有脚本；当前 B v3 保持，A v3 原规则恢复 |
| 后续脚本编辑、重复恢复 | 通过原型对照 | 冲突时不覆盖、不停止客户端；重复恢复为无操作 |
| 自动恢复原运行状态 | **未完成** | 测试关闭自动运行；重开客户端后需原生点击启动，CLI 原型尚未补齐此步 |

主要报告：flclash-naive-script-loses-standard-rule、flclash-a-updated-v3、
flclash-new-b-unmanaged、flclash-a-v3-after-restart、flclash-b-v3-restored、
flclash-a-v3-restored、flclash-restore-conflict。

## 4. 对实现顺序的约束

1. 保留共用 Mihomo 生成能力；两款客户端各自处理挂载位置、原生重新生成和恢复记录。
   测试共享脚本生成、进程及文件能力，客户端元数据流程分别维护，不复制整套编译器。
2. Verge 不能仅靠改全局脚本完成接入。先验证可靠的原生应用触发与逐订阅扩展组合，
   再证明新订阅和用户后续编辑的处理；不能看到工具组存在就显示“已生效”。
3. FlClash 不能直接切脚本模式丢弃标准扩展；需验证完整组合或其他原生挂载方案。
   在新订阅原生应用之前没有持续约束的方案尚未成立，切换后轮询补写不能充当严格保护。
4. 恢复使用所有权记录和冲突检查，只撤销本工具改动；不能回滚整个配置目录或数据库。
   补齐恢复前运行状态、部分失败及中断重试后，才可称为产品一键恢复。

macOS 的应用目录、控制器发现、权限、重启、系统代理和 TUN 均未专项验收；Linux 结果不能代替。
真实服务、DNS/WebRTC、脚本执行失败是否安全、任意用户脚本/标准规则组合、远端 provider、
客户端升级及操作并发也未覆盖。UDP 编译缺口继续由 F009 跟踪。
复现步骤见 [VM 说明](../tests/p0/client_vm.md)；产品验收条目见 [测试计划](../TEST-PLAN.md)。
