# F012 P0 覆写优化

日期：2026-11-04（Asia/Shanghai）。状态：Verge 已接管订阅的原型修正通过；完整 P0 仍未通过。
本轮只修改 tests/p0 和开发文档，没有改应用业务代码，也没有访问日常客户端或生产网关。
首轮结果保留在 [F011](F011-隔离客户端验证.md)，本页说明后续修正及其范围。

## 1. 根因与修正

| 已确认的问题 | 本轮修正 |
| --- | --- |
| Verge 的逐订阅脚本执行更晚，可以覆盖全局脚本 | 保留原全局与逐订阅脚本，在各自执行后复用同一生成逻辑；已登记订阅的最终服务规则优先 |
| 只改持久文件不会自动更新运行内核 | 从当前原生运行配置生成候选，隔离执行原生 -t 校验，经原内核 API 热加载；不要求用户手动刷新或重启 |
| 原生脚本异常会保留输入配置，可能回到原出口 | 先安装逐订阅的静态拒绝规则/组；用户脚本异常由包装捕获，整个脚本无法运行时仍有输入阶段保护 |
| 看到代理组存在不能证明实际路径 | 应用与恢复在返回成功前验证实际 TCP 链路和转发记录；不把对象存在当作“已生效” |
| 同域名 UDP 或旧连接会混入 TCP 诊断 | 同时匹配域名、TCP 和本次本地源端口；缺失或不唯一均拒绝给出成功证据 |
| 多文件覆写需要保留恢复边界 | 先保存所有权收据并整体预检；逐文件复核，恢复原字节；运行核对失败保留可恢复状态 |

独立 YAML/JS 生成能力在两款原型之间复用。Verge 流程拆为持久文件计划、原内核应用、
带收据的协调入口；通用控制器传输隐藏在一个测试积木内，没有复制整套编译器或增加应用框架。
这是 P0 测试模块内部的 L1 生成/传输/文件积木与 L2 应用/恢复流程分工，应用代码不依赖这些夹具。
当前热应用使用 guest 已有 JavaScriptCore 执行同一脚本，只是隔离验证依赖，
不是给产品新增 JS 运行时承诺。接口依据 [JavaScriptCore C API](https://developer.apple.com/documentation/javascriptcore/c-javascriptcore-api?language=objc)。

## 2. 真实客户端证据

环境沿用 F011：离线 Ubuntu ARM64 VM，Verge 2.5.10 / FlClash 0.9.2，内置 Mihomo 1.19.33。
服务和前置/落地/回显均为本地合成数据，系统代理和 TUN 关闭，不代表真实 AI 服务验证。

| 场景 | 结果 | 主要报告 |
| --- | --- | --- |
| 用户逐订阅 DIRECT 原生基线 → 安装最终覆写 → 再原生更新 | 通过，用户脚本保留，目标实际改经固定落地 | opt-verge-user-direct-baseline、opt-verge-profile-priority-fixed |
| 热应用与热恢复，保留另一条真实长连接 | 通过，客户端 PID 和无关连接 ID 保持，只关闭目标旧连接 | opt-verge-hot-cycle |
| UDP 显式拒绝与阳性对照 | 通过，目标无回包；无关 TCP 和 UDP 对照可用 | opt-verge-udp-guard |
| 用户脚本抛错 | 通过，目标 TCP/UDP 拒绝，无关请求正常 | opt-verge-user-throw-denied |
| 全局和逐订阅整段脚本均解析失败 | 通过，输入阶段静态保护仍拒绝目标 | opt-verge-native-syntax-denied |
| 原生脚本执行触发运行限额 | 通过，目标拒绝，无关请求保持；清除后恢复原落地 | opt-verge-native-limit-denied、opt-verge-after-native-limit |
| B v3 → v4、A v2 → v3、A/B 切换与客户端重启 | 通过，目标落地、后续节点、原用户规则及普通出口保留 | opt-verge-b-v4-updated、opt-verge-a-v3-switched、opt-verge-b-v4-after-restart |
| 全局或逐订阅脚本在接管后被用户编辑 | 通过，恢复前拒绝覆盖，客户端不停止 | verge-restore-conflict、verge-restore-conflict-profile |
| 恢复原用户脚本、再清理合成冲突 | 通过，用户 DIRECT 先恢复；测试冲突清理后回原机场，B v4 保留 | opt-verge-b-v4-restored、opt-verge-final-clean |
| FlClash 共用脚本兼容性与恢复 | 通过局部 TCP 对照，标准规则及 A v3 保留 | opt-flclash-shared-script、opt-flclash-shared-restored |

只有已接管订阅验证了静态保护。故障注入后先确认拒绝，再清除并确认健康，才开始下一项，
不把上一次的拒绝状态当成下一项证据。恢复成功也要核对实际路径，不只核对文件或进程。

本轮证据：dev-data/p0/client-vm/evidence/20261104T120343Z/。
包含 48 份报告（19 份 opt- 本轮报告及其他历史/冲突对照）、3 份合成源记录和 SHA-256 清单；
报告数量不是通过项数。原始证据被 Git 忽略，未导出数据库、偏好、控制密钥或恢复收据。
本轮测试覆写和故障注入均已清理，测试进程及 VM 已正常停止。

## 4. 仍需完成的条件

1. **新订阅的持续保护**：本轮为安装时已有订阅挂载静态保护；后来新建、恢复导入或未登记的
   订阅没有同等保证。全局脚本正常继承不能替代整段脚本失败下的保护，需先证明原生挂载方案。
2. **FlClash 接入**：仍只有逐订阅脚本；通用标准规则组合、新订阅约束和重启后恢复原运行状态
   都没有解决。本轮共享脚本兼容性通过不能升级成完整客户端支持。
3. **原生缓存和并发**：当前热应用复用已有运行配置；客户端导出/运行配置缓存和 UI 通知尚未
   专项验证。准备前后有版本复核，但多个文件与内核之间没有跨进程原子事务；并发切订阅、
   用户改挂载点、全部故障与中断场景仍需补齐，不能据有限检查宣称消除了所有竞争条件。
4. **真实产品范围**：当前只生成一个合成服务，原型只识别已知简单恢复规则；任意用户脚本/
   合并规则、远端 provider 和升级迁移未完整覆盖。macOS 专项、真实服务、DNS/WebRTC 和
   普通模式 UDP 未验。产品 UI、自动发现与独立恢复入口尚未实现。

继续 P0 时先解决新订阅的原生约束与 FlClash 能力边界，再进入完整产品适配；不把本轮
局部修正记为 P0 通过，也不让后台切换后补写替代切换前的保护。
