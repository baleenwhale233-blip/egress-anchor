# F010 ChatGPT / Codex 严格模式

更新：2026-11-04。状态：整篇教程 11 项已映射到产品与验收，部分合成域名 P0 对照通过；产品入口尚未实现。

## 1. 服务范围

- ChatGPT 模板包含 Codex 已约定的模型与认证入口，默认共用出口和严格开关，保持三个首批模板。
- Claude 与 ChatGPT 分别开启严格模式，默认关闭；开启其中一个不修改另一个的出口或严格设置。
- 模板维护核心访问、认证和必要资源域名，不能只靠两个基础域名就宣称完整覆盖。
  具体清单按版本、来源及实测维护；自定义 API 网关需显式补充域名。
- Codex 发起的第三方工具、浏览器、MCP 和远端云任务不因本地 GPT 模板而自动获得相同路径。
  仍按目标客户端接管和域名规则的实际范围说明结果。

## 2. 严格策略

1. 服务规则优先于原订阅的通用 AI/智能分流，其他服务继续原规则。
2. 出口沿用用户的服务选择。选定 ISP 时保持最终落地；故障不改用普通机场或直连，
   原落地恢复后按既定流程恢复连接并复检。
3. 显式拒绝命中受保护服务规则的应用 UDP，保留所需的 TCP 通路。
   不通过关闭整机 UDP 实现，不改变前置节点所需的底层传输。
4. 核对该服务的 DNS 出站和 IPv6 覆盖；涉及全局设置时说明影响并确认，沿用变更记录和恢复。
   多个严格服务需要的全局设置统一管理，关闭 GPT 不撤销 Claude 仍需的配置。
5. 保持正常连接复用；仅在用户切换、共享资源变更等约定动作时断开受影响连接。
6. 检测显示实际范围、时间和未验证项。语音等实时功能单独验收，说明严格 UDP 策略的实测影响。

## 3. 教程与官方资料如何使用

[用户提供的 Net.Coffee 完整教程](https://ip.net.coffee/gpt/codex.html)的 11 项全部作为参考。
以下编号对应文章顺序，是实现责任与验收映射，不代表文章中的效果判断已经得到验证。
能自动完成的适用项由严格模式处理；检查项展示证据；应用或用户控制的事项提供对应指引。

| 编号 | 关注点 | 本工具的处理与验收 |
| --- | --- | --- |
| C01 | 出口资源 | 管理用户自备 ISP，检查认证、可达性与观测出口；归属信息有来源才展示，不把 ISP 标签或评分当作可用保证 |
| C02 | 落地保持 | 保持用户指定的落地资源；前置可自动切换，最终 ISP 不自行更换；沿用已确认决策，不新增公网 IP 漂移锁或自动换 IP |
| C03 | 传输约束 | 对命中严格服务的应用 UDP 显式拒绝，保留 TCP/HTTPS/WSS；以可用 UDP 对照证明阻断，检查无关服务及前置传输保持 |
| C04 | TLS 能力 | 核对内核、协议和字段适用层；仅评估本工具管理且确实支持的配置。代理链外层 TLS 与应用内层 TLS 分别说明，后者无证据时标未验证 |
| C05 | DNS 路径 | 分开核对加密、解析器和出站路径，配置服务相关解析约束；节点引导解析及其他服务分别处理，不能只看 DoH 地址判定通过 |
| C06 | IPv6 范围 | 严格服务采用受控的 IPv4 路径并验证 IPv6 绕出边界；若需要全局关闭/修改，说明影响并确认、记录原值、支持恢复，不能仅凭字段判定全路径受控 |
| C07 | 服务识别 | 维护模型、认证及必要资源域名的版本化清单，覆盖 ChatGPT/Codex 的约定入口；不把共享 CDN、系统校时等目的地未经核验全部归入 GPT |
| C08 | 分流优先级 | 独立服务规则先于订阅通用规则；验证智能分流不会改变最终落地，未配置服务沿用订阅。自动前置与固定最终出口分别处理 |
| C09 | 连接生命周期 | 核对内核保活能力，减少无必要的重载/重连；验证长连接持续和只断受影响连接。内核 TCP 保活与应用连接池复用分开判断 |
| C10 | 请求负载 | 提供并发和重试的使用建议及可核验的诊断指引；网关连接数不冒充任务/请求数，不默认套用固定的单 IP 任务上限或接管 Codex 调度 |
| C11 | 链路效率 | 保持必要的前置到落地链，参考实际整链可达性与延迟选择前置；不额外叠加中转，也不凭节点名称或地域推定路径优劣 |

每项记录操作归属、适用范围、预期配置、实测证据及状态。可配置项要核对运行态；
不支持标明具体能力限制，缺少证据标未验证；使用建议不伪装成已执行的系统控制。
普通界面仍为服务出口和一个严格开关，C01-C11 的细节按需展开，不要求用户逐项配置。

### TLS 字段需要按内核解释

[Mihomo TLS 文档](https://wiki.metacubex.one/config/proxies/tls/)中的 fingerprint 是证书指纹，
client-fingerprint 才是特定出站协议的 uTLS 设置。因此教程中的 fingerprint: chrome
不能直接照搬；具体支持范围还要按固定内核版本复核。设置代理 TLS 字段也不能单独
证明 ChatGPT/Codex 的内层 HTTPS 指纹已变成浏览器指纹。
模板应明确提示适用层，避免静默改写原订阅节点或用无效字段表示“已加固”。

### 保活和并发要区分控制层

[Mihomo 全局配置](https://wiki.metacubex.one/config/general/)定义 TCP 保活项，
是否可热更新以及影响范围由客户端适配核对，涉及全局时沿用确认和恢复流程。
[OpenAI 官方 API 限额说明](https://developers.openai.com/api/docs/guides/rate-limits)按模型、
组织/项目等条件描述限额；不能将教程的经验数字设为所有 ChatGPT/Codex 用户的硬上限。
首版不通过解密应用请求来计算任务并发；用户指引与代理连接观测分别表达。

### 认证与流式连接仍需单独验收

[OpenAI 官方认证文档](https://learn.chatgpt.com/docs/auth)说明 Codex 的 ChatGPT/API key
登录方式及浏览器登录流程，也提到本地回调可能被网络配置阻断；因此认证和本机回调
分别验收，不能为了服务分流把本机登录回调送到远端代理。

[官方 WebSocket 文档](https://developers.openai.com/api/docs/guides/websocket-mode)提供持久
WebSocket API 通道。TCP 策略需保留 HTTPS/WSS 通路，不把“仅 TCP”误做成禁止
WebSocket 或强制所有请求使用短连接。真实 Codex 版本的传输方式与登录仍需实际验收。

## 4. 已完成的 P0 对照

使用同一固定 Mihomo、现有编译器和本机代理，以 chatgpt.p0.invalid/codex.p0.invalid
代表两个入口，测试代码见 [GPT 严格场景](../tests/p0/gpt_strict_checks.py)。

- 两个合成入口的 TCP 隧道均经过同一个 GPT 受管理落地，运行连接链路可核对。
- 两个入口的应用 UDP 均被显式拒绝。
- GPT 单独严格的对照中，Claude 保留其独立出口和原 UDP 策略，无关直连 UDP 保持可用。

这不是实际 OpenAI 域名、HTTPS/WSS 握手、登录、语音或桌面客户端的通过结果。
拒绝规则仍在测试夹具中，产品的模板/自动生成/界面需随 P1/P3/P6 实现。
